# Preparation, definitions and instance lifetime — v6.0

The exact preparation requirements are owned by [Planning](../spec/planning.md).
A compiled plan set is an optional representation, not the Engine's universal
unit of execution, publication or physical ownership.

These lifetimes do not impose one execution representation. The
[runtime profile contract](../spec/runtime-safety.md) distinguishes compilation
reuse, independent logical authority, executor independence and runtime/storage
independence. The shared finite and continuing Action kernels preserve semantic
transitions while Host and caller-owned implementations retain different native
programs, services, work/results and funding. Neither a borrowed schema nor a
shared kernel certifies reusable native compilation or all-profile execution.

| Object | Identity, content and lifetime |
| --- | --- |
| TD/TM revision | Description/model, not execution authority |
| Prepared definition | Immutable semantic/native content with checked dependencies; no live credential, handler, session or cleanup obligation |
| Registration | Linked implementation/configuration and supported facets; not a network endpoint |
| Logical instance | Consumed/exposed local identity, policy, behavior association, generation and publication |
| Execution capacity | Independently supplied/acquired funded storage and progress/cleanup; no cardinality equality with idle logical associations |
| Admitted work | Call, Action invocation, subscription or exposure participation with independent authority and funded release |
| Native infrastructure | Binding-owned listeners, sessions, subscriptions, pools, workers and buffers; may serve multiple logical owners |
| Deployment | Runtime/process/firmware owner, with its own failure and recovery boundary |

URI-variable declarations/schemas and required references likewise belong to
immutable shared meaning. Actual values and resolved destinations belong to
admitted work; optional stable instance operands remain independent of logical
authority. Concrete Bindings qualify native expansion/matching compatibility.
No Thing/device or Thing/connection cardinality follows from these lifetimes.
See [variable preparation](../spec/planning.md#uri-variable-preparation).

The [HTTP definition contract](../spec/binding-spi.md#explicit-http-definition-compilation)
provides one concrete compile-once / checked-bind-many representation using
the existing owned compiler interface. Its immutable request instructions and
original physical funding are separate from each mapping's checked endpoint,
exact execution registration and live instance binding. It does not turn that
HTTP representation into a required Engine program, cache or per-Thing owner.

The notification Host path likewise retains one actual prepared mapping while
binding independent logical associations and supplying conversation capacity
separately. Its native program remains endpoint/registration specialized. Original
service-owner import and prepared-declaration fencing follow
[Planning](../spec/planning.md#open-consumer-notification-preparation); original
occurrence policy and retained work follow
[Runtime Safety](../spec/runtime-safety.md#notification-associations-and-conversation-capacity).
This does not qualify authenticated source provenance or cross-endpoint lowering.

Continuing Consumer Actions apply that distinction through reusable qualified
`ConsumerActionDefinition`, independent `ConsumerActionAssociation` and separately
funded `ConsumerActions` capacity. Definitions stay endpoint/registration
specialized and retain original data/native declarations. Invocation identity,
opaque continuation and cleanup belong to admitted work, beyond each exchange.
Detailed contracts remain in [Core](../spec/interaction-core.md),
[Planning](../spec/planning.md#continuing-consumer-action-preparation) and
[Runtime Safety](../spec/runtime-safety.md#continuing-action-associations-and-invocation-capacity).


Producer reuse has a different publication boundary: a `PreparedThing` remains
one description's complete selection, while concrete HTTP response/validation
instructions can be explicitly shared across checked native route bindings.
Independent final-TD qualification, behavior/authority, native readiness and
collision checks, publication and retirement stay with each exposure. The
[Producer contract](../spec/planning.md#reusable-producer-preparation) owns the
exact split; it does not copy the Consumer association representation or make
an entire prepared Thing a universal reusable program.

Prepared security requirements are immutable content; credential services, verified
principals and opaque per-call capabilities are live dependencies/work. Native key
and trust owners remain in the Binding. Content sharing never shares permission.
A physical content owner survives every borrowed reference. Each logical owner
supplies its own reference, operand and record storage. Prepared-definition identity and logical
instance generation are independent; a plan-set epoch exists only if that object
is independently retained/replaced.

Consumer admission interprets common meaning once and reports support per
operation. Native lowering can be eager or a bounded first-use job above
execution. A deferred candidate can prove unsupported; actual use waits for its
complete selected preparation. An execution-only composition reports preparation
required for an unprepared Consumer operation.

Producer advertisement is stricter: every retained final Form/effective operation
must be fully qualified before Serving. Only pure construction whose support is
already established may be deferred, with owned normalized input, actual provider
association and funded bounded coordinator. If complete support checking cannot
be separated reliably from lowering, construct before publication.

Closed native setup may precede final endpoint binding and final TD qualification.
The candidate owns the endpoint and its rollback. It acquires exact member
slots once final selection is known, using any slots already promised by their
owner. Until publication the candidate keeps ingress closed. Final dependency/cancellation checks and
local installation are one non-fallible publication boundary.

Optional caches require bounded entries, work/waiters, negative-result policy,
stale-completion fencing and reclaim ownership. Automatic caching, serialized
images, code generation, interning and cross-Thing pooling are not prerequisites.
