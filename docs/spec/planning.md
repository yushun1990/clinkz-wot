# Preparation and capability selection — v6.0

Planning owns selection, complete support assessment and pure construction;
TD owns common interpretation. Native execution belongs to Bindings, and live
logical authority/publication belongs to Servient. These are semantic contracts,
not an invented universal compiler/program representation.

The modern TD selection/compiler integration currently uses Host registrations
and funded definition owners. Those are implementation choices, not required
representations of prepared meaning. Core's borrowed `ValueExecution` can lend
the exact finite value content from that output to a different execution owner;
the lender retains its original storage and funding. A caller can also supply
the same checked source-independent meaning without invoking Planning at runtime.
Neither construction path bypasses actual native/codec/security qualification
or current instance permission. The constrained Read demonstration does not port
TD-driven preparation or establish a second schema/operation interpretation.

`PREP-ISOLATION-001`: Preparation MUST be bounded, side-effect-free local work
over TD-resolved facts and captured actual registrations/configuration. It MUST
NOT acquire sockets, sessions, tasks, credentials, handler calls or execution
permission. Selected output MUST own all required execution facts independent
of the source. Deferred input MUST own a bounded normalized snapshot including
mapping-relevant extension metadata, never a runtime source-TD callback. Pure
incremental construction may acquire capacity before each step; failure retains
provisional output and funded bounded rollback. Copy/atomic lowering is an
optional adapter, not open compiler eligibility. There is no universal
all-native-bounds-before-any-pure-start barrier.

`PREP-SELECT-001`: Support is the intersection of the exact operation, Form
context, protocol/subprotocol, payload/response formats and parameters, required
schemas, security, native address/matching semantics, profile and policy.
Selection MUST be deterministic and explainable under bounded candidates/probes.
An explicit selector narrows admitted meaning and cannot weaken security or
invent a different operation. Pair the actual compiler/executor/configuration,
codec, validator and security implementations: format/type/hash/operation/scheme
indexes alone are insufficient. Refuse ambiguity rather than select by accidental
registration order. Preserve native collection semantics. Fallback shares the
owning search's remaining allowance wherever repeated probes require a lifetime
bound. An uncertain effect MUST NOT trigger automatic retry.

For finite responses, selected support includes every primary/additional
alternative of that Form/operation: its exact media parameters, default or
response-specific data role/schema, declared success, actual validator and
unambiguous executable native identification. A Consumer may select supported
interactions from a larger TD, but cannot select only the convenient response
branches of an interaction. A Producer checks known draft requirements before
native setup and qualifies every advertised alternative on the exact final TD
before publication. Unsupported branches cannot disappear from the published
description. Native status/header/content discrimination belongs to
the actual Binding, not common Planning. Scheme/type/media indexes do not prove
that complete pairing.

Common response preparation preserves additional-response order, applies TD
media/success defaults and resolves named schemas inside the selected semantic
closure. Its builder bounds schema construction and rollback while retaining the
owned response set. Current preparation bounds additional constraints together
to 64 nodes and 4096 name bytes, at most 32 additional entries. Checked content
reuse compares the complete response set without reconstructing replacement
schema owners. Request media remains a distinct mapping operand; an unused
request role does not require an encoder for that media. Present unconstrained
response data and absent output remain distinct. Exact executable scope is
[response evidence](../evidence/td-responses.md).

`PREP-DEFER-001`: Consumer admission MUST normalize/index common meaning once
and return per-operation support information. Default admission requires at least
one statically supported interaction; a caller MAY require a stricter set. TD
tooling need not admit any executable interaction. Coarse eligibility and fully
prepared support MUST be distinguishable. Eager or bounded cancellable first-use
native preparation is permitted; a deferred Consumer candidate can still prove
unsupported. No operation executes before its complete selected preparation,
validation/security and capacity checks. First-use latency/failure is observable.
Warm execution MUST NOT rescan TDs or repeat shared defaulting. The optional
preparation coordinator owns work/input/waiters separately from live calls and
installs immutable results into generation-checked slots; execution-only
compositions report preparation required for unprepared Consumer operations.

`PREP-REUSE-001`: Prepared immutable content, local instance authority and native
infrastructure MUST have independent identities and lifetimes. Prepare-once /
checked-bind-many is permitted when the Binding establishes invariant dependencies
and valid operands, including endpoint/configuration/schema/security/profile
facts. A name/hash/type match grants no compatibility or permission. Each instance
retains fresh authority and its actual reference/operand/record cost; shared
backing retains its physical owner/original account until final release.
Specialized per-instance preparation is also valid; no parameter language,
universal VM, cache, persistence or generator is mandatory. A separate plan-set
epoch is required only when independently retained/replaced, not for every Thing.

Compilation-work reuse MUST bypass the invariant lowering for compatible
instances. Sharing semantic content, sharing transport or interning separately
compiled output does not establish that claim. Distinguish actual lowering from
input validation, dependency comparison, checked operand binding, admission and
native specialization. The concrete Binding owns the dependency/operand split;
its complete actual configuration and all facts its lowering observes must be
checked. A mismatch refuses or explicitly compiles another definition before
dependent effects. Source/instance identities and registration coordinates are
not dependencies merely because an old compiler carrier includes them.
The HTTP Consumer increment uses one typed input extraction for lowering and reuse,
with derived input equality; it retains no independent semantic projection.
This is a concrete Binding choice, not a required generic compiler framework.

Compilation reuse does not establish executor or runtime/storage independence.
Sharing a semantic schema or transition kernel across representations does not
establish native lowering reuse. Compatible dependencies are checked within each
actual Binding representation; incompatible environments need not use identical
native artifacts. The [runtime profile contract](runtime-safety.md) distinguishes
these claims from independent logical authority and their executable evidence.

`PREP-COVER-001`: Require at least one Form on every retained Property, Action
and Event. Before Producer Serving, every final root or affordance Form, each
effective operation and every advertised alternative MUST have complete support
under one configuration effective through the local publication decision. This
covers the eligible registration set, selected Binding and services, every
competitor whose refusal establishes uniqueness, and the registered behavior
or an explicitly supported aggregation path. Check native addressing/matching, subprotocol,
formats/response branches, required schema rules, security, and promised Action,
subscription/cancel/Event-response behavior. One preferred Form/default operation/
security alternative or a draft Covered marker cannot certify others. There is
no live late-handler exception and no advertise-now/Unsupported-later policy.
A deliberately reduced TD must pass the complete final process itself. [TD 1.1 InteractionAffordance](https://www.w3.org/TR/2023/REC-wot-thing-description11-20231205/#interactionaffordance)

Support may be established by constructing the mappings, or by the actual
Binding's equivalent complete support check followed by deferred pure
materialization. The latter is optional: it MUST establish every condition that
could discover Unsupported for the exact final description/dependencies. If that
cannot be separated reliably from construction, construct before publication.
The exposure separately pins executor/configuration and actual codec/security/
behavior registrations plus the funded materialization owner/input/coordinator.
The immutable definition contains no live handler/authority/cleanup obligation.
Materialization may fail from ordinary capacity/cancellation, but deterministic
unsupported meaning already present at publication is a qualification defect.
It completes before dependent native effects, dispatch or validated delivery.
An execution-only Producer materializes required data before installation.

When a Binding learns an address during closed setup, resolve the final base
and qualify the resulting Forms against all eligible registrations, including
previously losing competitors. The final selection can split or combine draft
members. Acquire storage for the actual final members. A shortage refuses the
candidate and returns its protected owners through rollback. It cannot remove a
competitor, alter Form preference or manufacture coverage. Native collisions
and readiness belong to the actual Binding. An immutable final TD can reuse
coverage only while every relevant dependency remains current through commit.
For a source-free Producer, require current coverage for the supplied final
meaning or refuse until the caller supplies a freshly qualified definition.

URI preparation validates base/templates. Dynamic variables use shared bounded
prepared expansion, followed by Binding-native address checks. Destination policy
and credential audience cover actual expanded/proxy/redirect/continuation targets.
A description is not permission to contact arbitrary referenced addresses.

Optional caches retain bounded work, waiters, negative-result policy and stale
completion/reclaim ownership. No unconditional single-flight/cache layout or
one-off operation resource schema is mandated without an actual cache contract.

## Existing implementation disposition

Whole-Thing Producer preparation also selects Property observe/unobserve and
Event subscribe/unsubscribe Forms against actual family-qualified notification
source registration. A Property source supplies no finite Read/Write behavior.
The MQTT capability interprets its
own resolved vocabulary, captures common prepared data meaning and the exact startup
registration, and rejects unsupported control data, dataResponse, response
branches, security or other effective operations. It creates no native subscriber
or socket during preparation. Composed publication binds the original native
mapping and actual validation/security services to the qualified final TD.
Closed installation verifies that exact pairing. The concrete supported subset is owned by
[the MQTT README](../../protocol-bindings/protocols/mqtt/README.md).

The previous 2,180-line plan-set/API projection is superseded; its exact revision
is available at the v5.1 basis in the authority map. Current Planning Property
Read APIs remain restricted: the borrowed aggregate has eager all-bounds-first
ordering and the Host adapter accepts Copy atomic output. Their tests keep those
narrow claims. They MUST NOT constrain the successor compiler or be multiplied
per interaction family as its implementation. The authority migration itself implemented no replacement compiler or first-use
coordinator. The open finite Consumer path now uses the portable
`ConsumerCompiler` contract and generic owned Host erasure; the old support
carrier and sealed aggregate are explicitly named `InlineConsumer*`. The Host
Producer now also has a whole-Thing selector: each advertised Form/effective
operation asks the actual linked capability registrations for independently
owned concrete definitions. Missing Forms, ambiguous support and missing
behaviors refuse before native setup. Final qualification checks the complete
retained TD against those definitions and all eligible registrations. Opaque owned definitions are not
a universal program/session ABI; native readiness and collisions remain separate
Binding obligations. Consumer first-use coordination and broader service,
schema and security implementations remain outstanding.

Final whole-Thing checking walks the complete common meaning and compares each
original definition at its exact scope/Form/operation and actual registration.
The selected provider checks its existing definition and current dependencies;
other registrations perform complete support probes to detect new ambiguity.
Planning observes the actual set and all mutable inputs before the first probe.
Servient carries their validity through the commit with the closed native
owners. Repeating independent Form probes cannot establish this invariant. Support probes
and final comparisons use the same matching/refusal semantics as preparation,
not operation/type/identity tags. Their sequential callback temporaries require
an actual declared peak bound before managed Host invocation; callbacks retain
no new controlled backing after return. A missing or newly excessive bound
cannot borrow unreserved capacity. A provider may temporarily materialize data
inside that funded bound; no allocation-free compiler representation is imposed.

## Open finite Consumer implementation

`open_consumer::ConsumerRegistry` captures actual startup compiler/executor and
codec/validation/access service owners. Each compiler bounds its actual
construction, scratch and disposal. Incremental and owned output are eligible.
General typed/static pairing
uses the same actual configuration contract without compiler-name tests. The
restricted `InlineConsumerCompilerSupport` is neither consulted nor issued by
open admission. Its old general public names and conversion methods are removed.

Basic admission and the existing common whole-description Form walk are reused
without Producer publication qualification. One bounded semantic arena per Form
lends resolved `FormOwner`/operation facts to the actual candidates. The general
compiler input has no logical Property Read record or mandatory TD id. The
Consumer reports each Form/effective operation, including unsupported alternatives;
at least one selected interaction is required. TD Form order is the default
preference; multiple actual supporting providers within one admitted Form refuse.
An explicit binding/Form selector only narrows candidates after common services
have accepted the meaning. Selection keys include affordance kind/name and
operation, so same-named
Properties and Actions do not collide. The current finite facets are Property
Read/Write and `InvokeAction` with explicit `synchronous: true`. Continuing and
unspecified synchronicity use the separate Action facet below. Thing-root
ReadAllProperties, ReadMultipleProperties, WriteAllProperties, WriteMultipleProperties and QueryAllActions use the finite facet; other
collection operations use their distinct notification facets or remain unsupported.
Action input/output use distinct prepared schemas; absent roles permit no
application data. Repeating the Form's default response media preserves that
absence. A response-specific schema establishes a present value; different
media alone cannot establish a schema-less opaque result, and current common
preparation declines that combination for an Action without output. One actual
captured data service must execute every selected request and
response representation and constraint. Different media are allowed when that
complete pairing is qualified; they do not require a new codec abstraction.

Read and Write select independently on the same Property, including one Form
with default or explicit multiple operations. A Write captures the complete
supported Property value schema as input and no response value role. Property
readOnly/writeOnly declarations constrain eligibility even when a Form explicitly
contradicts them. Unsupported value assertions, effective security or concrete
Binding response mappings remain reported Consumer alternatives; a selector
cannot weaken them. Complete Producer qualification still requires every retained
effective operation, actual behavior and mapping. It cannot keep a Read while
silently dropping an unsupported advertised Write.

Eager preparation lends the actual compiler a bounded semantic view. For a
resumable compilation retain that view, its cursor, output and scratch while
they overlap. A repeated search shares its job-local allowance with compiler
probes and alternatives. Yield keeps the cursor. Early return, cancellation,
failure or invalid output unwinds its provisional owners without publishing
a partial mapping or performing I/O.

`ConsumerExecutionContent` captures immutable affordance, operation, selected security requirement and data-role
meaning without endpoint, service, authority, policy or account fields.
`PreparedConsumerContent` is its funded Host owner. Ordinary preparation constructs
that content once; `prepare_with_content` qualifies actual endpoint mappings for
one retained operation by comparing borrowed source assertions against the same
content. The reusable subset includes Property Read/Write value constraints and
ReadAllProperties member constraints. Included member names,
order and complete supported assertions must agree for the collection; nested
object fields/required names compare by meaning, independently of source order.
No replacement constraint/member/name tree is built. Unsupported or changed meaning refuses. Other Forms remain
reported Consumer alternatives, rather than becoming Producer qualification.

Every selected mapping still passes common Form/security/media/URI checks, actual
provider selection, complete data-service support, native preparation and capacity
checks. `ConsumerDefinition` retains the shared content, exact native mapping,
actual executor/configuration and data service with captured bounds. A change to
native literals or headers requires native qualification and either another
compilation or an explicitly established reusable definition. Checked new endpoint
operands may bind an existing definition; a specialized artifact has no implicit
retargeting right. Changing values within a qualified dynamic mapping is interaction
work and requires no replacement definition. Content reuse grants no native
artifact compatibility. Native compilation remains owned/incremental,
and no TD, parser, semantic arena or compiler survives the completed definition.

Finite definition construction qualifies complete schema/media and native
operation/URI capability once and captures each actual service's
`qualification_revision`. Support answers MUST remain stable within that
revision; mutable providers and wrappers MUST advance/propagate a non-reused
revision before changing qualified support. The revision method is required:
implementations must explicitly declare fixed support with zero or supply live
invalidation. A default zero is not an adoption of this contract.
Execution compares original revisions, availability and resource declarations;
it MUST NOT repeat complete capability qualification as a liveness test.
Source-free instance binding cannot refresh an invalidated definition. Access
binding captures the required `ConsumerAccessService::qualification_revision`
covering complete security support and actual security dependencies. It replaces
the optional `security_revision` method, including existing credential-only
overrides, so every implementation and wrapper must explicitly adopt the combined
contract. Dynamic permission outcomes still require fresh authorization,
without retaining credentials or granting later permission. Revisions do not
replace per-interaction authorization, payload validation or native checks.
The [explicit HTTP implementation](binding-spi.md#explicit-http-definition-compilation)
uses the existing owned compiler interface for both fresh lowering and supplied
definition binding. A `ConsumerCompilation` job therefore denotes bounded native
preparation, not necessarily a new invariant lowering. Other compilers retain
their own actual dependencies and specialization rules.

`type_schema::prepare_schema` captures the bounded structured subset defined in
[Core](interaction-core.md). A bounded borrowed census checks supported assertions,
nodes, names and depth. The builder bounds actual allocation and rollback.
Scalar input/output roles now own their dynamic constraint storage; their actual
bytes and disposal work are no longer zero. Reuse uses `matches_schema` or the
named-member comparison against borrowed TD facts, without compiling another
constraint tree. Actual data services still qualify the retained complete schema.
Finite, continuing Action and Notification preparation share the same borrowed constraint
census, construction and compatibility interpretation. `prepare_type_schema`
remains an explicit narrower participant facet; it is not a consequence of a
continuing lifetime. Root Action status and actual MQTT collection mappings
retain narrower implementation subsets. A JSON service alone does
not extend a native participant's admitted operation/profile scope.

HTTP Producer selected-definition final checking compares borrowed normalized
constraints against the original program and retains its existing schema owner;
it no longer recompiles a second selected constraint tree merely to compare it.
Other providers still need complete actual support probes, with declared scratch.
The explicit [Producer definition path](#reusable-producer-preparation) also
checks and binds fresh native endpoints without repeating invariant lowering.
Whole-description admission remains separate work; neither path establishes
general normalized-TD reuse.

## Reusable Producer preparation

`PreparedThing` is the complete selected mapping set for one description, not
the unit of cross-instance reuse. Its scope/Form/operation coordinates, actual
provider indices and bound native definitions remain description-specific.
`ProducerCapability::prepare` may lower fresh instructions or check and bind
explicitly supplied immutable work; it returns the concrete mapping for the
current input in both cases. This does not require a second common compiler ABI,
whole-Thing cloning or the Consumer definition/association representation.

Every new instance still runs the complete TD admission/semantic walk, actual
behavior coverage, deterministic provider selection and native operand checks.
Managed admission qualifies the entire immutable final TD, exact mappings and
all eligible providers. Closed installation verifies actual native operands
and consumes that qualification under the current configuration.
A shared subdefinition grants neither final-TD qualification nor permission.
Changed dependencies refuse a supplied definition; there is no implicit fallback
compilation in the explicit bind path.

The concrete [HTTP contract](binding-spi.md#reusable-http-producer-instructions)
separates response/validation instructions from native route binding. All
applicability checks run through the same compiler entry before either lowering
or borrowed comparison; schemas compare using the existing common comparators,
and native response facts compare directly with the retained discriminator.
No second independently maintained dependency tree is stored. Actual lowering
is counted only where response/schema instructions are constructed. Ordinary
fresh support probes may still lower temporary definitions; the supplied HTTP
definition path and selected final checks bypass that work.

Shared instruction, schema and response backing stays with its original owner
through every mapping and native configuration snapshot. Each instance supplies
space for its references, operands, behavior and publication. Temporary checking
space ends with the check. [Runtime ownership](runtime-safety.md#reusable-producer-definition-ownership)

Binding an existing Consumer definition attaches its actual access policy
without recompilation or source callbacks. Servient supplies independent
current authority and admits work separately. A changed service cannot become
a new baseline by binding another instance. Refusal returns the original
mapping/policy owners. A definition can be bound after the source is retired.

A composition root adopts each actual service once and imports its retained
owner across registries and Servients. Raw alias matching within one startup
construction cannot discover independent adoption elsewhere. Each registry
supplies its own records and native registrations. Refusal unwinds those claims
and returns protected inputs. Retained users keep the original service and
native owners through their final normal or late result.

## URI-variable preparation

PREP-SELECT/COVER/REUSE-001 apply to the complete effective variable meaning of
each selected interaction. Common preparation uses TD's effective-scope view,
qualifies every retained declaration/schema assertion, checks RFC expression
support and declaration coverage, and owns source-independent names, schemas
and reference requirements. Native compilation qualifies expression placement
and actual configuration compatibility. It does not reinterpret DataSchemas.
Reuse compares effective schemas and reference requirements without constructing
another shared content owner; different native literals/addresses may share this
meaning under separately qualified mappings.

An unresolved template is not a concrete destination or credential audience.
Definition/instance preparation checks actual services and native eligibility;
it defers actual-destination permission to bounded pure native resolution and fresh
instance authorization for each interaction. This grants no permission to make
I/O during preparation/resolution. Static mappings retain their preparation
destination check. Unsupported selected assertions or missing native resolution
support refuse the candidate, with no fallback during accepted execution.

Producer qualification remains complete for the entire final description.
Dynamic publication requires fully supported native matching/captures, variable
validation, collision handling and all advertised operations before Serving.
A Consumer expansion utility cannot establish that claim. The current HTTP
finite Property Producer continues to refuse URI-variable declarations/templates, including
unused retained declarations. It never drops them to obtain qualification.
Existing qualified native Action continuation-ID mappings retain their separate
profile; they do not acquire general caller-supplied variable support here.

## Continuing Consumer Action preparation

`ConsumerActionRegistry::prepare_action` admits one named Action with absent or
false synchronicity. Explicitly synchronous Actions use the finite facet. Each
described Query or Cancel needs a Form, an eligible provider and a native mapping
that accepts the original Invoke continuation. An absent control stays unavailable.
An explicit Form or Binding selector for any operation must admit a complete
combination, including that operation. Once the TD index is complete, preparation
refuses a required operation with no admitted Form or an explicitly selected
Binding ID absent from the observed registry. Either result precedes native compilation.

TD 1.1 allows a Consumer to choose a usable Form. ClinkZ prefers the first viable
combination in TD Form order, comparing Invoke first, then Query, then Cancel.
Each operation may use a different registration. For the preferred Form
combination, exactly one assignment of actual providers must qualify. A second
compatible assignment reports `AmbiguousBindingOwner`. An unsupported pairing
can give way to another provider or Form during preparation. Registration order
has no preference and execution never replays an uncertain effect through an
alternative. [TD 1.1 Forms](https://www.w3.org/TR/2023/REC-wot-thing-description11-20231205/#form)

For a fixed Invoke Form, compare each Query Form across all eligible Invoke
providers before moving to the next Query. Within that prefix, compare Cancel
Forms across all Invoke providers that can use the selected Query. Omit an
absent control from the ordering. An earlier Query takes priority even if it
needs a later Cancel. Multiple providers at a partial combination matter only
if they can complete it. Each control accepts the original Invoke independently,
so changing Query cannot rescue an Invoke for which every Cancel was ruled out.
Preparation stops when it establishes uniqueness or ambiguity at the first
complete Form combination. Its second complete provider assignment decides
ambiguity immediately, including when the final operation is Invoke itself.
Qualification work is limited to alternatives that can still determine
preference or a tie.

The Host registry indexes the selected Action's Form coordinates and resolved
addresses during one Basic admission and URI walk. When the search needs an
operation on a Form, it reserves candidate storage for that operation. All
registrations allowed by its selector share one loan of the Form's resolved
semantics. If another operation on that Form is needed, it obtains a fresh
loan using the same admission's lifetime balance. A Form with all three roles takes at most three loans.
The search reuses each completed Form/operation result, including an empty
provider set, while it can still serve a candidate combination. An empty result
releases its candidate buffer and temporary storage before the next probe. The
Form index keeps the result so later Invokes can skip that qualification. If
every eligible Form for a required control has returned an empty set, every
Invoke is ruled out.
A nonempty set whose mappings reject the current Invoke can still serve a later
Invoke. Once an Invoke Form has exhausted its controls, preparation releases its
mappings and reuses its candidate storage for the next Invoke Form. The compiled controls
remain available to later Invoke providers. A hard compiler or continuation
compatibility error on a required probe propagates before I/O, as does exhausted
capacity or work.

The search bounds its Form index and partial assignments. Account for actual
overlap of the TD walk, semantic arena, candidate mappings, schemas and compiler
scratch. Acquire usable storage at the builder that needs it. Dispose rejected
mappings, retaining any rollback scratch until disposal. Reuse available
scratch on the next probe. The chosen mapping survives the closing configuration
observation. A job with repeated scans debits the same remaining allowance
before each delegated visit or probe. Report exhaustion separately from lack
of support.

The composition owner chooses how the search observes one effective configuration.
Use `try_new_fixed` when the inputs are immutable or all changes are serialized
with preparation. With `try_new_revisioned`, supply a bounded passive observation
of the whole registration set. All writers that can change native support,
continuation compatibility, data eligibility or preparation access must participate.
The observation returns a non-reused stable revision or `None` while changing.
A change between the opening observation and the decision, or an observation
during an update, refuses with `StaleHandle`. This covers the rejected alternatives
that establish preference and uniqueness. A later competitor affects future
searches. Each instance independently authorizes use of its selected operations.

The actual `ConsumerActionPreparation` compiles pure bounded native mappings,
while Planning prepares the same bounded structured data meaning as finite
execution and checks the current endpoint NoSec subset. Input and output are
independent `ValueSchemas` roles. Bound their construction and destruction by
the supported shape, and retain the actual variable backing. One original
owned pair serves Invoke, Query and Cancel. Each Form checks its borrowed
assertions against that pair once when schema qualification succeeds. Each selected
data service qualifies the complete schemas for its application-value roles.
Invoke qualifies input and possible completed output, Query qualifies completed
output, and Cancel carries no application value. Query need not support the input schema. Native status/acknowledgement
encoding is the mapping's responsibility. Different operations may retain
different valid media and body/scratch/work policies for the same output meaning;
Query output is never required to fit Invoke's representation or allowance.
No native compiler needs to reinterpret constraints to obtain common meaning.
Native vocabulary, variable address placement/matching and response conventions
stay in the Binding; variable scope and DataSchema interpretation are shared.
The reusable definition owns every selected mapping, both Action data roles,
actual data-service owners and original definition funding after all TD/compiler
owners disappear. `ConsumerActionRegistration` imports `RetainedConsumerServices`
from startup composition. Each service has one backing owner referenced across
operations, definitions, registries and families. Each distinct owned media
snapshot, mapping and schema needs storage at its actual builder.

Preparation captures the complete data policy/media/support, native identity,
operation and applicable exchange, continuation, result and scratch bounds.
It checks actual services and their relevant configuration around access/compilation
callbacks. `ConsumerActionDefinition::check_dependencies` preserves those facts
through complete association and new-work admission; construction cannot
capture a replacement baseline. Already admitted execution follows the
[dependencies of its owned operations](runtime-safety.md#continuing-action-associations-and-invocation-capacity),
rather than importing unused controls into its invalidation scope. A changed
declaration, even a smaller bound, requires explicit new qualification and
applicable funding. The preparation access service is a
qualification dependency, not a retained Consumer permission. Execution binds
explicit per-operation access owners independently, checks their actual backing,
qualifies destination/NoSec support and retains the original service revisions.

An already qualified, endpoint-specialized definition may be bound to independent
Consumers without repeating TD admission, schema construction or native
compilation. This is reuse of the same actual definition, not checked bind-many
of new TDs or cross-endpoint partial lowering. Bindings keep continuation
compatibility and native capacity; shared definitions imply no shared logical
authority or extra physical exchange capacity.
A typed preparation facet must bound each callback, including any delegated
work. Split a large compilation into bounded steps or refuse its supported
input size. Exhausting capacity returns provisional owners without effects.

## Open Consumer notification preparation

Host `ConsumerNotificationRegistry<D>::prepare_notification` admits one target
and notification kind. It visits applicable Forms in TD order and stops at the
first viable Form. A Form or Binding pin narrows the search. Each visited Form
lends one set of resolved facts and role schemas to every eligible registration.
A compiler or native executor declining a candidate leaves the other providers
on that Form eligible. A second qualified provider reports
`AmbiguousBindingOwner`. Exhausted work or capacity refuses before native I/O.

Registrations may have unrelated program, configuration, participation and
response types. At startup, `RetainedConsumerNotificationRegistration::into_provider`
takes a constructor from its concrete `ConsumerNotificationDefinition<B>` to
the deployment's output `D`. An application can use the variants of its own
enum and dispatch the selected definition to its typed conversation capacity.
Planning calls the constructor once after a successful decision. Homogeneous
startup adoption and retained-owner import produce a `TypedConsumerNotificationRegistry<B>`
and return the concrete definition directly. A homogeneous registry is `Send` and
`Sync` when its registered Binding is. A mixed registry can hold local Bindings
and a local revision observer.

Use `try_new_fixed` for immutable eligibility or a search serialized with all
writers. With `try_new_revisioned`, the deployment supplies one bounded, passive
observation covering native configuration, data and access eligibility across
the registered set. It returns a non-reused revision or `None` during an update.
The closing observation covers earlier rejected Forms, competing providers and
the decision to report ambiguity or missing support. A changed or unavailable
revision refuses with `StaleHandle`. Later searches observe later competitors.

`ConsumerNotificationPreparation::compile_notification_form` qualifies the
resolved Form on the actual source-free Binding. A provider accepting
`contentCoding` must implement that coding for the selected data roles.
The notification execution profile currently qualifies fixed endpoints, the
simple endpoint NoSec requirement and Forms without explicit response branches.
TD resolution applies the Thing's `base` to relative references. Notification
preparation requires the resulting href to be a concrete URI with a scheme.
It skips unexpanded templates and references that still need a base before
destination authorization or native compilation.
Planning checks the actual data service's availability, media and schema
support, and the access service's security support and destination permission.
Before native compilation, the data service must support establishment and
occurrence delivery on the selected Form. Once the Binding qualifies its program,
the service must also support the data for each mapped cancellation and each
reply the program can offer, even when the caller may decline a reply. Each
executable scalar role uses `supports_media` for the Form representation.
Collection facets also require the service's exact primary media. The source-free
definition repeats both checks against the retained program and service.
Selection tries authorized candidates first. If every alternative fails and a
destination was denied, revisit the relevant Forms under the same TD admission,
job-local lifetime bound and configuration decision. A native mapping that
qualifies with its destination denied establishes `AuthorizationDenied`.

The TD walk, semantic arena and compiler scratch can coexist with selected and
competing native mappings. Bound that actual peak. The first qualifying definition
owns its schemas and lends them to later probes. Refusal disposes provisional
mappings with their rollback path. The selected immutable definition retains
its backing through handoff. Metadata, support, clone and disposal callbacks fit
within the job's inclusive operation bounds.

The selected `ConsumerNotificationDefinition` owns the actual Binding/program,

## Selected executable security preparation

`security::prepare_security` projects complete effective security from shared TD
facts, including Form replacement of Thing requirements, conjunctive lists and
nested Combo alternatives. Standard scheme operands, proxy and requested scopes
remain part of meaning. Absent optional credential names stay absent; only a
concrete Binding supplies protocol-specific placement defaults. Unsupported interpretation (such as extension assertions)
becomes an explicitly unavailable leaf, never NoSec. Cycles, malformed combinations
or bounded expansion failure refuse the whole expression before selection.
Structural dependencies and full standard expansion counts remain checked even
inside a proxy-bearing or extension-bearing unavailable Combo; opacity cannot
hide a cycle or reduce its processing cost to an anonymous branch.
Public typed inputs must pair each built-in discriminator with its matching TD
variant; `Extension` carrying a built-in name refuses before selection rather
than concealing its standard semantics as unavailable extension data.
The current projection admits at most 64 visited nodes, depth 8, 16 complete
alternatives and 4 non-NoSec components per conjunction; its 1024-unit text/operand
envelope also charges reference/scheme names and 32 units per parameter. These
are processing limits. Bound the actual temporary expansion and keep rollback
available. The original prepared content owns its variable backing through disposal.

Consumer preparation tries complete conjunctions in declaration order. For each
it requires the actual access service and native compiler to support that same
conjunction, together with independent operation/data/configuration qualification.
`ResolvedBindingInput::selected_security` lends the exact chosen conjunction;
a native compiler must not independently choose a different alternative. Provider
ambiguity within that conjunction refuses. `ConsumerExecutionContent` retains
only the selected meaning, without endpoint, credentials, policy, trust or live
authority. Checked reuse must find that complete meaning in the new effective
expression and repeat actual service/native qualification; it cannot silently
choose a different branch. Unselected unsupported branches are not Consumer
support claims and remain disqualifying for full Producer advertisement.

Producer compilation without a Consumer selection qualifies the complete
expression. Every advertised alternative must execute with the actual paired
services, including native placement/multiplicity and operation support. Pure
security refusal precedes native setup; final qualification after allowed closed
setup still rechecks the complete advertised expression, original services,
configuration, endpoints and readiness. It never prunes unsupported alternatives.

Live credentials and mutable revisions belong to instance services. Per-call
capabilities follow fresh audience/instance permission at each effect.
Rotation invalidates old bindings and unread results. Checked

Fresh rebinding never revalidates prior work. No compiler or source callback
